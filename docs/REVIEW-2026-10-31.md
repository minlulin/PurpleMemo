## 1. Executive summary

PurpleMemo is a Tauri 2 desktop app: Rust backend + React 19 / TypeScript
renderer, one encrypted local SQLCipher database, no accounts, no sync, no
cloud. Scale: ~161 source files, ~69 k lines (TS/TSX/Rust/scripts), 31 tables +
one FTS5 virtual table, 28 Tauri IPC commands, 852 automated tests.

**The codebase is in unusually good shape.** The 2026-11-01 `docs/AUDIT.md` is
accurate as far as I can check: every remediation it claims is actually present
in the tree, the gates it reports green are green here, and none of its
"checked and found correct" claims are false. Its 37 findings were dominated by
real performance work at realistic data volume; those fixes are in.

What remains is **not** a fresh crop of bugs. It is:

1. **One live documentation drift** that a release operator would act on (`R1`).
2. **One toolchain/onboarding defect** that blocks the very first command in
   the README on a common Node version (`R2`).
3. **The largest unverified risk in the project**: the audit's own Rust changes
   (schema migration 5→6, nine indexes, `synchronous=NORMAL`, `prepare_cached`,
   FTS trigger narrowing) were written **without a compiler**, and the Rust
   half of `npm run verify` has not been run on this branch (`R3`).
4. **Four remediation items the audit deliberately deferred** and that are still
   open, two of which are user-visible at scale (`R4`).

Nothing found here is a data-corruption bug or a security regression. The
security-sensitive surfaces (SQLCipher key handling, path traversal, IPC header
decoding, the LAN-share consent/consent-token, the reset engine, AES-GCM tag
handling in `crypto.ts`) read as sound and, in several places, deliberately
designed against specific attack shapes.

## 5. New findings

### R1 — `docs/RELEASE.md` still documents schema v5 while the code is v6 — **Medium (release-procedure drift)**

`docs/RELEASE.md:154` reads:

> **Schema migrations are forward-only, and downgrading is unsupported.** The
> current schema is v5 (`inbox_items`, `links`, `trash_items`, and the v5
> unique `photo_refs` index plus the `reminders` due-index)…

But `src-tauri/src/schema.rs:21` is `pub const SCHEMA_VERSION: i64 = 6`, and
`MIGRATION_5_6` adds nine hot-path indexes. The audit bumped the schema and
updated `AUDIT.md` but missed the living procedure doc.

**Impact:** a release operator following `docs/RELEASE.md` is misled about the
current schema version and the index set. The *rules* (forward-only, no
downgrade, three edits to add a version) are still correct — only the version
number and the enumeration are stale.

**Fix:** change "v5" → "v6" and append the 5→6 index set to that paragraph.
**Effort:** 10 min.

### R2 — `npm install` hard-fails on Node 22/23 and the README never says Node ≥ 24 — **Medium (onboarding)**

- `package.json` declares `"engines": { "node": ">=24" }`.
- `.npmrc` sets `engine-strict=true`.
- Measured on Node 22.22.3: `npm install` aborts with `EBADENGINE … Required:
  {"node":">=24"}, Actual: {"npm":"10.9.8","node":"v22.22.3"}`. This is a hard
  failure, not a warning.
- `README.md`'s **Development** section says only `npm install # once` — it
  never states the Node requirement. The first command a new contributor runs
  (or the first command the README tells them to run) fails.
- The audit itself is internally inconsistent: `docs/AUDIT.md §8` says
  "node ≥ 22 is enough to run the TypeScript side", while the manifest gates the
  install behind Node ≥ 24.

**Impact:** on the still-supported Node 22 LTS, a fresh clone cannot install at
all, and the README gives no hint why. Node 22 is an LTS line with years of
runway, so this will bite real contributors.

**Fix (pick one):**
1. State the requirement: add a line in `README.md → Development` —
   "Requires Node ≥ 24 (the `engines` field is enforced)." — and note that the
   TS-side gates run on Node 22 only via the relaxed install.
2. Or lower `engines` to `>=22` **and** keep it honest by running the TS gates
   on Node 22 in the local gate. (Not recommended: the manifest is deliberately
   pinned, so documenting is cheaper and truthful.)

**Effort:** 15 min.

### R3 — The audit's Rust changes were never compiled — **High (unverified risk)**

`docs/AUDIT.md §10` states it plainly:

> **Rust is not compiled here.** This sandbox has no `cargo` and no crates.io
> access, so the `schema.rs` / `db.rs` changes (PERF-09, PERF-10, SCHEMA-03,
> SCHEMA-04, and the migration 5→6 test) are written against the code as read
> but **have not been through a compiler**. Run
> `npm run test:rust && npm run clippy && npm run fmt:check` before merging.

That instruction is in the audit, but **`npm run verify` includes those three
Rust gates and nothing on this branch has run them.** The changes touch the
one file that is hardest to get right without a compiler (`schema.rs`) and the
one path that must not break on an existing user's database (the forward-only
migration, the FTS trigger, the durability pragmas).

This is the single largest open risk in the project, and it is *known to the
audit*. It is listed here because it must not be lost between the audit and the
next release.

**Fix:** run the Rust gate on a machine with `cargo` (and crates.io) before any
release or merge that touches `src-tauri/src/schema.rs` or `db.rs`. Concretely:
`rustup component add clippy rustfmt` then
`npm run test:rust && npm run clippy && npm run fmt:check`.

**Effort:** minutes to run; potentially days if a migration test fails.

### R4 — Four audit items are still open, two user-visible at scale — **Low/Medium (deferred)**

The audit closed most findings but explicitly deferred these. They are still
open in the tree:

| ID | What | Still present? | User-visible? |
| --- | --- | --- | --- |
| **DUP-08** | exporter re-reads `collections`/`loans` instead of the repos | ✅ `exports.ts:923, 974` | no |
| **DUP-11** | `scripts/measure-search.mjs` rebuilds the search SQL | ✅ `scripts/measure-search.mjs:294` | no (measurement drift) |
| **PERF-11** | `habit_logs` read is unbounded (all history, ever) | ✅ `habits.ts:127` | yes — ~11 k rows on first paint at 10 habits × 3 years |
| **PERF-12** | no multi-read IPC; Dashboard = 11 round trips per reload | ✅ no `db_query_many` | yes — Dashboard/Budget first paint |

PERF-11 needs a product decision on best-streak semantics; PERF-12 needs a
Rust command + driver + mock + tests, which is exactly the half that cannot be
compiled here (`R3`). These are correctly deferred; they are listed so the next
pass does not lose them.

**Effort:** DUP-08 ~45 min · DUP-11 ~45 min · PERF-11 ~4 h (decision-gated) ·
PERF-12 ~1 day (Rust-gated).

### R5 — `latest.json` release notes are frozen at schema v5 — **Info (acceptable, note for next release)**

`latest.json` and `RELEASE_NOTES.md` (both the 0.1.0 release) say the schema is
"currently v5". These are the *released* artifacts for 0.1.0, so they describe
what shipped on 2026-10-24 — before the audit's 5→6 bump. That is correct for a
frozen release, but the next release's notes must say **v6**, and the updater
manifest must be regenerated with `scripts/make-latest-json.mjs`. Flagging so the
version is not copied forward unnoticed.

### R6 — `docs/AUDIT.md` is dated 2026-11-01 — **Info**

The audit's header says `Date: 2026-11-01`, one day after today (2026-10-31).
Cosmetic; the commit it audits (`aa8a6cf`) is correct. Not a defect.

### R7 — `check-hooks` "warn and exit 0" path can still yield a green-looking gate — **Info (accepted)**

When the check is run outside a git checkout (or with no `git` on PATH), it
warns and exits 0, so `npm run verify` can report green with no hook running.
The README calls this out as intentional. It is a real, accepted hole: in a
source tarball there is no hook to arm. Worth remembering when reading a green
`verify` from someone who did not `git config core.hooksPath .githooks`.

## 6. What is genuinely excellent

Credit where it is due — several of these are rare in a single-developer
codebase:

- **The local gate is real and self-enforcing.** `check-hooks.mjs` *fails* rather
  than warns when the hook is unarmed, so a green `verify` cannot sit next to a
  dead gate. `check-versions.mjs` byte-compares the vendored `@noble/ciphers`
  copy against the installed package (verified identical here) — a drift check
  that most projects forget.
- **Test-pinned contracts.** The DDL, the trash column lists, the FTS trigger
  text, the export field mapping (`docs/EXPORTS.md`), the i18n catalogues, and
  the mock↔Rust refusal strings are all pinned by tests. A schema change that
  breaks an assumption fails the gate rather than shipping.
- **Schema safety.** Forward-only migrations, a step list asserted to cover every
  gap, a structural test comparing migrated vs baseline DDL, and the FTS trigger
  narrowed so a pin/archive no longer rewrites the index row.
- **Deliberate security comments.** The crypto module documents *why* base64 is
  validated strictly, why the vault tag is domain-separated and deliberately
  cheaper than the full KDF, and why `OperationError` has exactly one meaning.
  The renderer-trust-boundary section in `RELEASE.md` states an *accepted* risk
  and lists what would revoke the acceptance.
- **No dead weight.** No TODO/FIXME/HACK/XXX anywhere in source (the single hit
  is a test fixture `"OTHERXXX"`), no `unsafe` blocks, four `any`-adjacent
  matches that are all English words in comments, zero non-null-assertion
  misuse, and every `package.json` dependency is imported.

## 7. Prioritised recommendations

| # | Action | Finding | Effort | Why first |
| --- | --- | --- | --- | --- |
| 1 | **Run the Rust gate** (`test:rust`, `clippy`, `fmt:check`) on a machine with `cargo` | R3 | minutes (or days to fix) | The migration/pragmas are unverified and sit on the most dangerous path |
| 2 | Fix the v5 → v6 drift in `docs/RELEASE.md` | R1 | 10 min | A release operator reads this doc; it is currently wrong |
| 3 | Document the Node ≥ 24 requirement in `README.md` (or re-scope `engines`) | R2 | 15 min | The first README command fails today on a supported Node |
| 4 | Close DUP-08 and DUP-11 (small, self-contained) | R4 | ~1.5 h | Cheap, no product decision |
| 5 | Re-open PERF-11 with a product decision on best-streak horizons | R4 | 4 h | User-visible at scale once decided |
| 6 | Build `db_query_many` (Rust-gated, pairs with #1) | R4 | ~1 day | Dashboard/Budget first-paint, needs the compiler from #1 |
| 7 | Regenerate `latest.json`/`RELEASE_NOTES.md` for the next release at v6 | R5 | part of release | Don't copy v5 forward |

**Sequencing rationale:** #1 is a *verification* step, not a code change — do it
first, because it may change what #2–#6 mean. #2 and #3 are documentation and
block a human. #4 is cheap and mechanical. #5 and #6 are the only work that
needs a decision or a compiler, so they wait for #1.
